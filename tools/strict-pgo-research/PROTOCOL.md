# One-shot strict Engine PGO feasibility

This is a research-only study, not a production DSP or build change. Its hypothesis is that compiler-guided layout, inlining and specialization of unchanged Engine code can reduce CPU without changing its numeric behavior. A pass supports only this compiler, platform, profile and held-out corpus, not other CPUs, DAWs, modes or cross-platform fidelity. Existing terminal studies remain closed.

## Immutable inputs and isolation

`run.py` freezes source, tests and build-tree Git object IDs. GNU C++ 13.3.0 on the public repository's free standard `ubuntu-24.04` x86-64 runner is required; a different installed version stops, not silently substitutes. All subprocesses are pinned to the first allowed CPU with a child affinity witness. The 40-minute runner deadline includes compilation, training, qualification, tests and cost. The job ceiling is 45 minutes for setup/artifacts. Each benchmark invocation has a 300-second ceiling. Timeout or any failure terminates the experiment, with no retry, fallback profile or later amended gate.

Baseline and candidate both use `-std=c++20 -O3 -DNDEBUG`, ordinary generic target settings, and identical ordinary objects. No `-march=native`, fast math, source approximation or DSP edits. Only Engine.cpp receives profile generation/use flags. FactoryPresets, Ig00156Batch (with the existing `-ffp-contract=off`), stock benchmark driver and external qualification driver are compiled once and reused bit-identically. Each unchanged regression driver is also compiled once for both arms. Object/binary hashes and full commands are retained. Relevant unsafe/finite/associative math, errno, signed-zero and contraction option states must match.

The instrumented Engine is compiled to the exact same source/output path later used for profile-use compilation. The separate profile directory must initially be empty. Train **once**, using the unchanged stock performance quick suite at 48 kHz/128 samples, 16 held callbacks: selectors 0, 1 and 10, 15 cases and 36 rows. This includes the stock effects/modulation, pedal and release phases; it is not a speed assessment. The sole recursively inventoried Engine.gcda is copied and hashed before held-out observations. No subsequent training invocation exists. Missing-profile and coverage-mismatch warnings are fatal. Profile-use binaries must have no gcov/profile-runtime symbols. Profile/object/binary hashes are checked again before cost and afterward.

## Held-out correctness before cost

Both arms render the unchanged full baseline suite at 44.1 kHz/256, 16 held callbacks (27 cases/51 rows) and full performance suite at the same configuration (39 cases/100 rows). Every non-timing CSV field and row must match. Every rendered stereo float byte, including warmup, must match. A qualification-only external render wrapper records MXCSR, x87 status/control, errno and call frame counts with clean and preseeded exception flags. It saves/restores the caller's FP environment and errno. This wrapper is never linked into training or cost binaries and adds no internal lifecycle or event hooks. FP transcript and exact PCM sizes/hashes must match. This is a bounded FP observation, not a proof covering all exceptional inputs or rounding modes.

The unchanged SmoothingTests, ActiveTailContinuityTests and MpeMasterSmoothingTests run in both arms with 120-second per-test limits. SourcePerformanceAuditTests and FilterBatchEngineTests have 180-second limits. Both arms must pass and produce identical test logs. FilterBatchEngineTests uses only `--write-corpus`, **never `--benchmark`**; its complete existing nonempty PCM/state corpus must match byte-for-byte. This exercises oscillator residual/state, filter histories, ownership/envelopes, controller/mode/policy changes and idle/release behavior without new internal instrumentation. Tests stay at their original assertions/coverage. No benchmark is allowed after incomplete qualification.

## Frozen native cost phase

Use the unchanged stock callback-CPU timer, full performance suite at 44.1 kHz/256, **128 held callbacks**, all 39 cases/100 rows. The candidate and baseline have identical workloads and no qualification wrapper/profile generation. Checksums, nonfinite counts and all non-timing work fields remain equal on every run. CPU times must be finite, positive, marked available, have the exact callback call count and agree with the reported CPU/audio ratio. Every raw row is retained.

Primary: sum callback CPU seconds / sum audio seconds across exactly **24 source-performance warmed-held rows**, three scenarios for each unseen selector 2 through 9. Training selectors are excluded from this primary assessment. Secondary aggregates: all source-performance warmed-held, isolation warmed-held, legacy warmed-held and all 100 rows.

First run three independent baseline/baseline pairs (six executions). Each pair's primary, source-performance and all-row aggregate ratios must lie within 2% of one; isolation/legacy within 3%; every individual row within 10%. If any fails, the decision is terminal unusable calibration and **zero candidate cost executions**. No retry on another runner or adjusted workload.

Only after all three calibrations pass, run three baseline/candidate pairs in orders A/C, C/A, A/C. All three primary candidate/baseline ratios must be below one. The geometric-mean primary gain must be **strictly greater than max(0.5%, twice the largest absolute primary A/A deviation)**. Each secondary aggregate's geometric ratio must be at most 1.02; every row's geometric ratio at most 1.05. A useful small reproducible gain can pass; instruction-count reductions or correctness alone cannot. No post-observation tuning, retraining, alternate selector subset or result-based exclusion.

The job starts automatically only on this workflow's first run, first attempt, in a public repository. No dispatch trigger, larger/paid runner or retry is provided. Research publication/execution requires independent review first. An accepted feasibility result does not authorize shipping this profile or enabling PGO in production; compiler/profile distribution, compatibility and representative target-hardware validation remain separate work.

## Interpretation and limits

A failed calibration cannot establish either benefit or regression. A failed gain gate closes this exact candidate/profile without retesting. Any correctness/profile/compiler/deadline failure is an incomplete study, not an optimization result. The hard deadline may end the study before cost if release tails or shared-host contention are expensive; it will not reduce coverage to finish. Public standard hosting and pinning do not imply stable hardware. A passing trial measures this held-out corpus only, with unavoidable limited sample and host generalizability.
