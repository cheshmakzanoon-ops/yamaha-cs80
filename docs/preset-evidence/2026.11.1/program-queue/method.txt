# Assignment 47 — native VST3 Program queue diagnosis

## Finding

**Confirmed pre-existing controller-dependent Program queue limitation.** A native VST3 Program change submitted only through `IAudioProcessor::process` does not load the requested factory program in the tested Linux module. Adding an `IComponentHandler`, allowing JUCE's running internal message thread 250 ms, using a nonzero audio block, and moving that process call to a separate thread do not cause the queued program to load. Calling `IEditController::setParamNormalized` for the same Program value does load it.

The omitted controller synchronization explains assignment 44's queue-only fixture result. The result is not caused merely by the absence of a component handler, an unserviced message loop, or the subsequent state readback. It must not be relabeled as an invalid queue. The Program parameter is actually advertised with `kIsProgramChange | kCanAutomate` (`0x8001`).

The refined factory data is not the cause. Both binaries tested show the same behavior, and the relevant processing/bridge source is unchanged from the pre-refinement commit. **Queue-only program automation is not certified.** The separately verified plugin Library/native-controller factory selection and native state restoration remain valid. No production source or pinned JUCE wrapper was changed during this investigation; implementing program loading on the audio path requires a separate integration change and qualification.

## Exact experiment

The small host reuses `tests/Vst3AutomationTests.cpp` and creates the actual native processor and controller. It initializes and connects both `IConnectionPoint` directions, synchronizes initial state, obtains native Program metadata, and selects curated **Flute, host index 374**, using normalized value `374 / 522`. The program list has 523 entries; Program parameter ID is **1886548852** with 522 steps.

Each Program queue also contains an ordinary volume change to physical value 0.31. This control proves the processing call accepts and applies ordinary parameter changes. The initialized fixture has metadata `Brass Swell I`, index 222, and default parameter values; those initial values are a fixture setup, not an assertion about that factory preset's actual content.

| Path | Result immediately after queue and after 250 ms | After explicit controller synchronization |
| --- | --- | --- |
| Zero-frame flush, no handler | Program remains index 222; volume becomes 0.31 | Flute index 374 loads |
| Zero-frame flush, handler installed | Same | Flute index 374 loads |
| 128-frame process, handler installed | Same | Flute index 374 loads |
| 128-frame process on a separate thread, handler installed | Same | Flute index 374 loads |
| Controller selection before the queue | Flute stays selected; queued volume becomes 0.31 | Already selected |

Every stage captures native component state **before any subsequent `setComponentState` readback**. Thus the stale program selection is already present in the processor state and is not manufactured by the readback. The controller-first positive control produces an asynchronous `kParamValuesChanged` handler notification during the same 250 ms interval; this is direct evidence that the internal Linux message loop is servicing notifications. The queue-only cases produce no handler edit or restart notification in that interval.

Both native module runs exit 0, with 26 logical observation groups checked by the recorded analysis, and 48 state snapshots total. Exit 0 means the diagnostic completed and its stated observations were checked; it does **not** mean queue-only Program selection passed.

## Why the route behaves this way

The pinned JUCE version is 8.0.11, commit `c352e2489000ffeb9e397051377d75eef2efe641`. Its VST3 wrapper creates an auxiliary `AudioParameterInt` for Program. The actual controller uses `ProgramChangeParameter::setNormalized`, which invokes the owner's `setCurrentProgram`; the plugin implementation then calls `loadFactoryPreset`.

The processor queue route updates the auxiliary parameter using `setValueAndNotifyIfChanged`. That helper sets the thread-local `inParameterChangedCallback` flag. `OwnedParameterListener` reaches the controller's `paramChanged`, which returns immediately while that flag is true. No later controller selection is scheduled by that route. Waiting or installing a handler cannot turn that suppressed callback into `setCurrentProgram`.

The product's generated HostAutomationBridge wrapper offers the parameter to `attachHostAutomationQueue`. Program is not one of the processor-owned APVTS automation lanes, so attachment returns false and the wrapper uses the same JUCE fallback. A zero-frame flush also retains that fallback. The generated VST3 wrapper in the two build directories is byte-identical, SHA256 `7f72937f4c1427bf036c04279736fa4c958ba18d6d470bc299f1cb595a99df64`.

`setComponentState` refreshes controller Program from the processor owner's current program index, not the auxiliary Program parameter. This explains assignment 44's readback, but is not the origin of the missing load.

## Protocol scope

Steinberg's official guidance assigns automation delivery to the processor queue and GUI synchronization to host calls of `IEditController::setParamNormalized`. It also restricts Program automation when affected parameters are themselves automatable. Consequently a full host must perform controller synchronization, but that obligation does not prove the processor-only behavior is correct or sample accurate. The present evidence establishes the precise controller dependency; it does not certify arbitrary DAW program automation, program-change timing, or every host protocol path.

- [VST3 Parameters and Automation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Parameters%2BAutomation/Index.html): Automation Playback, GUI playback, parameter flags and automation constraints.
