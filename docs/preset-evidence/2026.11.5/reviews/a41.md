# A41 — Parameterized installation artifact inspection

## Outcome and scope

Added a new explicit-input verifier for all four native installation targets.
It preserves the historical `.4` helper unchanged and has no default source,
run, attempt or factory revision. The expected repository has a documented
default; every supplied API and package identity must agree with it.

No actual `.5` native installation archive was supplied or qualified in this
work. Source `6094bce18c8b19da804c2fbc9a00e31969a7f579` was used only to exercise
loading the committed verification scripts and revision declaration. The
parent's subsequent corrected source can be supplied without changing this
helper.

## Implementation

The helper snapshots the install ZIP and both API receipts once, then hashes and
inspects those same immutable bytes. It rejects unexpected external symlinks or
nonregular files, duplicate JSON keys, unsupported outer ZIP objects and bounds
archive allocation before materializing the outer directory. The exact inner
archive, manifest and checksum names derive from the explicit source/platform.

`git show` loads the bundle and native header verifiers from the requested
commit into a private temporary directory. The source tree and five source
contract files are recorded. The explicit revision must match the source's
factory declaration, and the source packager must carry the known JUCE pin.
The working tree's verifier code is not executed.

The complete inner inventory, sidecar/embedded manifests and checksums are
verified by those committed scripts. A41 then checks all advertised executable
architecture/role headers, Unix execute modes where applicable, source/revision
and workflow declarations, exact `SOURCE.txt`, and clean JUCE 8.0.11 provenance.
Every manifest inventory entry and each native executable's byte count and hash
are retained in the output.

Report publication uses an atomic no-replace link from a completed private
file. Existing evidence, including a dangling output symlink, is preserved.

## Executed bounded checks

**Eleven test methods passed, zero failures and zero errors.** They include:

- Four positive inert platform/architecture fixtures.
- Four otherwise coherent wrong-CPU fixtures rejected by native-header checks.
- Thirteen API/run/repository/attempt/digest/size/name/expiry identity mutations.
- Mismatched explicit source revision, duplicate metadata keys, an extra outer
  entry, inner payload corruption with a matching outer digest, and a symlink
  external archive: twenty-two rejected mutations in total.
- An external-input race control that changes all three original files after
  their snapshots are taken; reported hashes and inspected content still agree
  with the original frozen bytes.
- A failed synthetic run context that remains failed, without inferring native
  success from internally consistent archive bytes.
- Preservation of an existing output file and dangling output symlink, with no
  temporary-file residue after the refused publication.

The fixtures contain inert executable headers and fabricated API values. No
product is executed. No native pass, authenticated acquisition or release
qualification is inferred from those tests.

## External requirements

Every report intentionally retains `release_qualified: false`,
`native_validation_passed: null` and
`artifact_attempt_binding_verified: false`. Supplied run metadata establishes
context; the current package and artifact metadata do not identify the producing
attempt. Authentic original upload logs and successful job/step outcomes must
bind the actual artifacts to that attempt. Complete native test rosters, original
validator exits and distributed-to-validated payload identity remain independent
gates, together with audition inspection and remaining-platform qualification.

Native headers establish advertised architecture and image role. They do not
prove runtime validity, exclusive universal-binary content, every DAW,
installation behavior, publisher signing/notarization, listening quality or
acoustic indistinguishability.
