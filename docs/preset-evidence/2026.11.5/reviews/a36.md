# A36 — Parameterized Windows/Linux VST3 payload binding

## Outcome and scope

Added a new [payload identity helper](../verification/a36-verify-validator-payload.py) for explicit source, library revision, run and attempt inputs. It is adapted from the historical [2026.11.4 helper](../../2026.11.4/ci/source-078c098/windows-linux-validators/verify-validator-payload.py), which remains unchanged. The production command has no old revision default and no option to disable source pinning.

The helper verifies the installation archive's complete manifest inventory, then compares every file, resource, inferred directory and symbolic-link target in its distributed VST3 bundle with the exact separate validator input artifact. File sizes and SHA-256 digests cover all file bytes. This is payload identity evidence; it does not execute a binary, establish API authenticity or prove native validation success.

**No new CI installation or validator artifact was inspected by A36. No native build is qualified.** The probe only used isolated, inert synthetic header/resource archives and existing repository source. Its source-header check observed commit `6094bce18c8b19da804c2fbc9a00e31969a7f579` with revision `2026.11.5`; this is not a claim about that commit's native CI outcomes.

## Required inputs and enforced checks

| Input | Enforcement |
|---|---|
| `--source` | Full lowercase 40-character commit SHA; package/verification scripts must equal their exact Git blobs at this commit. |
| `--revision` | Explicit canonical `YYYY.MM` or `YYYY.MM.PATCH`; must equal the source commit's `curatedLibraryRevision` declaration and the installation manifest. |
| `--run-id`, `--attempt` | Positive integers; no attempt inference or default. |
| `--run-api` | Plain run/attempt API JSON whose `id`, `head_sha` and `run_attempt` equal the caller's expected context. Status and conclusion are observations, never native acceptance decisions. |
| `--install-archive`, `--install-api` | Exact installation Actions ZIP plus its artifact API JSON: positive artifact ID, exact platform name, unexpired status, source/run, byte length and SHA-256 digest. |
| `--validator-archive`, `--validator-api` | Exact separate validator input Actions ZIP plus the same API checks. Its artifact ID must differ from the installation artifact ID. |
| `--platform` | `linux` or `windows`, both x86-64 in the reviewed workflow. |
| `--consumer-log` | Required for the known Windows compiler-sidecar container case. Exact downloaded artifact ID, size and digest, downloaded SHA, and the bundle selected by both original Windows validation invocations must match. |
| `--repo` | Repository containing the expected source commit and matching packaging/verifier scripts; defaults to the working directory. |
| `--out` | Fresh output path. Existing files are never overwritten. |

The source-pinned installation verifier checks the complete inner package, including embedded/sidecar manifest agreement, expected native architecture and formats, checksums, every declared path and payload digest, symlink safety, supported types, binary headers and the absence of extra or missing content. The outer installation artifact must contain exactly the expected inner archive, manifest sidecar and `SHA256SUMS`.

The separate validator ZIP receives strict inventory and path checks. Its full selected VST3 tree must match the installation tree. Missing resources, additional resources, changed binary bytes, changed link targets, duplicate members, malformed objects, unsafe paths and unexpected container objects are rejected. Parent directories are inferred where Actions omits directory records. Archive timestamps, ownership and permissions normalized by Actions are not compared between containers; the installation manifest's declared permissions are still checked by the source-pinned package verifier.

The exact Windows top-level `CS-80 Reference.exp` and `CS-80 Reference.lib` pair is recorded separately only when both files have the expected AMD64 COFF formats, the pinned source workflow uploads the whole VST3 output directory, and the original consumer log binds the exact downloaded artifact and explicitly selects `vst3\CS-80 Reference.vst3` in both required lanes. Other filenames, incomplete pairs and similarly named files inside the VST3 bundle receive no exclusion. Linux has no compiler-sidecar exclusion.

## Snapshot, resource and evidence handling

Each external ZIP is read once into a bounded immutable byte snapshot. Both its API digest comparison and ZIP inspection consume those same bytes. Replacing or modifying the original path after that read cannot silently substitute different bytes during inspection. Metadata JSON and the Windows consumer log are also read as bounded snapshots; duplicate JSON keys and nonobject metadata are rejected. The result records hashes of the exact API JSON snapshots supplied to the command.

The helper preserves the historical limits of 512 MiB per input archive, 256 MiB per regular payload entry, 1 GiB expanded payload, 4,096 members and 2 MiB metadata. New classic-ZIP preflight checks bound the central directory before Python materializes its entries. ZIP64, multidisk, unsupported compression, encryption and unexpected trailing data are rejected. Inputs must be regular files; nonblocking open avoids waiting on a FIFO, and final symlinks are refused where `O_NOFOLLOW` is available.

The package verifier and packager are read and compared to the exact source Git blobs, then imported from private temporary copies of those same bytes. This avoids reopening mutable checkout files after their identity check and does not create bytecode in historical evidence directories.

Reports are written completely to a private temporary file, flushed, then published with an exclusive hard link. An existing destination, including a competing writer's newly published report, causes refusal. The helper does not replace prior evidence. The output filesystem therefore needs ordinary hard-link support.

## External qualification gates

Every successful payload result explicitly contains:

```json
{
  "status": "distributed_vst3_matches_validator_input",
  "release_qualified": false,
  "native_validation_passed": null
}
```

Current GitHub artifact API records identify the workflow run and source, but do not identify the producing attempt. Current installation manifests likewise contain `workflow_run_id` without `workflow_run_attempt`. Matching the supplied run API's attempt therefore establishes context only. The report always leaves `artifact_attempt_binding_verified` false. If a future manifest declares an attempt, a mismatch is rejected, but a matching declaration still does not replace authentic original upload evidence.

The parent qualification review must independently establish:

1. Authentic API responses and downloads, exact source/tree and reviewed run attempt, artifact retention and the original successful producer/upload steps for each supplied artifact ID.
2. Original successful native jobs and build/test/package steps. An evidence artifact uploaded under `always()` does not establish job success.
3. The exact validator input artifact consumed by each original native validation job, with unsuppressed original step exits and all required randomized/fixed-seed lanes, strictness, GUI coverage, program counts and retry eligibility.
4. Windows and Linux installable payload identity using this helper on the actual new archives. Mac packaging, AU copy identity and Mac validation remain separate gates.

A supplied run API with `conclusion: "failure"` can still yield a successful **payload equality** observation when the two ZIPs agree. The result records that failure and leaves release qualification false. It must never be interpreted as a successful native run.

## Use on actual new artifacts

From the repository root, replace every illustrative value with the reviewed source/run/attempt and actual downloaded files. Use a fresh report path:

```sh
python3 -B docs/preset-evidence/2026.11.5/verification/a36-verify-validator-payload.py \
  --repo . \
  --source FULL_REVIEWED_SOURCE_SHA \
  --revision 2026.11.5 \
  --run-id REVIEWED_RUN_ID \
  --attempt REVIEWED_ATTEMPT \
  --run-api PATH_TO_AUTHENTIC_RUN_ATTEMPT_API.json \
  --platform linux \
  --install-archive PATH_TO_EXACT_LINUX_INSTALL_ARTIFACT.zip \
  --install-api PATH_TO_LINUX_INSTALL_ARTIFACT_API.json \
  --validator-archive PATH_TO_EXACT_LINUX_VALIDATOR_INPUT_ARTIFACT.zip \
  --validator-api PATH_TO_LINUX_VALIDATOR_INPUT_ARTIFACT_API.json \
  --out PATH_TO_FRESH_LINUX_PAYLOAD_OBSERVATIONS.json
```

For Windows, use `--platform windows`, the corresponding exact installation and validator artifact paths/API JSON files, and `--consumer-log PATH_TO_ORIGINAL_WINDOWS_PLUGINVAL_JOB.log` when the uploaded container contains the known compiler outputs. Preserve the resulting JSON alongside the authentic inputs and original job/step evidence. Keep its `release_qualified: false` unchanged; a separate consolidated qualification record can cite it after the external gates are satisfied.

## Executed synthetic checks

Retained evidence:

- [Probe source](../verification/a36-payload-probe.py)
- [Probe log](../verification/a36-payload-probe.log)
- [Structured synthetic observations](../verification/a36-payload-probe-results.json)

The final run passed **13 tests with zero failures and zero errors** in approximately 1.1 seconds. These tests include **58 rejected mutations**: 24 inherited payload/sidecar cases and 34 additional context, integrity, resource and evidence cases. They also retain three inert Windows/Linux platform controls and five explicitly named contract controls. These are fixture counts, not native CTest, pluginval or listening results.

The new negative cases cover wrong source/run/attempt metadata, missing explicit CLI context, revision disagreement, optional manifest-attempt disagreement, wrong artifact identity/digest/size, duplicate archive entries with refreshed API digests, oversized ZIP directories, trailing ZIP bytes, malformed metadata, nonregular/oversized inputs, replacement after a snapshot, and attempted evidence overwrite. Controls verify that a concurrent output race produces one complete report and one refusal, that file replacement cannot change the bytes already inspected, and that failed native-run metadata is never promoted into native success.

During probe development, one assertion initially required a digest-mismatch message after replacing a ZIP. That replacement also changed its compressed length, so the helper correctly rejected it earlier on API size. The assertion was corrected to accept that earlier integrity rejection; the dedicated digest-mismatch case remained separate and passed. No helper acceptance rule was relaxed.

To rerun the bounded synthetic probe, choose a fresh output path:

```sh
python3 -B docs/preset-evidence/2026.11.5/verification/a36-payload-probe.py \
  --out PATH_TO_FRESH_SYNTHETIC_RESULTS.json
```
