# A31 — real-time cost of the instrument-body continuation

## Method and actual scope

Compared the exact `c76ad288e02fbeca48f39652bf4fcdd99837f793` InstrumentBody headers with committed source `fcc3c8e055223fe4f786ca162ff46076c33471c8`, using GCC 14.2.0, C++17 and `-O3 -DNDEBUG`. This is a **direct body microbenchmark**, not a complete Engine, plugin callback, DAW, or native-platform performance qualification. It avoids mixing the old 202-parameter Engine ABI with current headers. Source SHA-256 receipts and every observation are retained in [summary.json](../verification/a31/summary.json).

The final [paired harness](../verification/a31/paired-body-cost.cpp) compiles both exact header versions into separate namespaces in one executable. It pins itself to one allowed CPU, alternates execution order for adjacent baseline/candidate pairs, warms each case once, and records seven measured repetitions. It uses process CPU time so time spent descheduled does not directly appear as rendering work. Hardware retired-instruction counting was unavailable: Linux `perf_event_open` returned `ENOENT`. These timings retain frequency, cache and virtualization variability; they are not instruction counts.

Each rendering case runs **16 bodies**, 12,000 internal samples each, at **96 kHz internal / 48 kHz host**. Eight registers spanning MIDI 48–76 are doubled, with velocity 0.8, brightness 0.55, decay 1.2, size 1 and pressure 0.2. Steady pitch is compared with a precomputed continuous ±3-semitone sinusoidal movement, avoiding pitch-generation math inside the timed region. The note-on case measures 8,192 starts, each followed by one tick. Identical old/current inputs are used. New material cases compare their actual new selector with the old corresponding generic model; these are intentionally different oscillator banks and sounds.

Initial separate-process runs showed substantial order-dependent noise even in unchanged models. They and a reverse-order repeat remain in the evidence folder, but the table below uses only the adjacent paired run. **378 paired measurements** completed with finite checksums and **zero measured allocations** in note starts and audio ticks.

Moving wind bodies have median added cost of roughly **5–15%** in this isolated body workload. This is the expected work of evaluating fixed-Hz responses and their bound at a pitch-changing control boundary. Moving new banjo/koto/harp bodies measure approximately **12%, 24% and 14%** above their old generic-model comparisons. These are observed tradeoffs, not claims of zero cost.

The Gong's 20-mode bank costs **1.925×** the old generic bell during motion (paired range **1.895–1.954×**), and **2.074×** during steady rendering. Its moving candidate median is **17.364 ms CPU** for the specified 16-body, 12,000-sample workload. More modes and independently delayed onsets replace the much sparser old generic bell. Music Box and Kalimba are cheaper in this workload, reflecting their smaller dedicated banks. It would be misleading to convert these body-only ratios into whole-plugin ratios: the circuit engine, rank envelopes, effects, host handling and the changed factory recipes are not measured here.

Unchanged steel/nylon/bass moving controls have medians **0.994 / 1.038 / 0.942×**, but some timing ranges are wide. The result supports bounded extra work and identifies where it occurs; it does not establish a hard callback deadline or prove a general speedup.

## Storage and code-path audit

The maximum mode bank remains **48**, harmonic response arrays remain **24**, and the control period remains **16 internal samples**. The correction reuses the old bowed/vocal response arrays. `sizeof(InstrumentBody)` is **6,088 → 6,096 bytes** in this compiler, an eight-byte increase from material selection and alignment, or 128 bytes across 16 body objects. Thus “no new response-array storage” is accurate; “no object-size change” would not be.

The new fixed-Hz response functions use bounded arithmetic and resonance divisions at note start or a pitch-changing control boundary. New material trigonometric, power and exponential spectral construction occurs at note onset. The per-mode sample rotation has no new transcendental operations, allocations or locks. Existing periodic coefficient refreshes and unit-rotation normalization remain. All arrays and loop bounds remain fixed; the measured allocation counter confirms zero allocation for every tested note-on/tick workload. This does not independently audit unrelated plugin/UI paths.

No production code, parameter range, preset, test gate, or remote state changed in this assignment. The measured additional body work is retained openly as a precision/cost tradeoff; native full-plugin validation remains separate.

## Reproduction

From the repository root, extract both baseline headers into `/tmp/cs80-a31/before/` using `git show c76ad288e02fbeca48f39652bf4fcdd99837f793:src/core/<header>`, where the two headers are `InstrumentBody.h` and `InstrumentBodyVariants.h`. Compile `docs/preset-evidence/2026.11.6/verification/a31/paired-body-cost.cpp` with `c++ -O3 -DNDEBUG -std=c++17 -I/tmp/cs80-a31 -Isrc/core`, then run it with affinity limited to one CPU from `os.sched_getaffinity(0)`. The complete source, affinity receipt, raw [paired.csv](../verification/a31/paired.csv), sequential/reverse diagnostics and hashed summary are retained.
