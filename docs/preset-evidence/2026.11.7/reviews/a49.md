## Source reasoning

The snapshot helper, editor, processor, mailbox, and display files all match the frozen source byte for byte. Their SHA-256 values are recorded in `evidence.json`.

1. **The clear occurs before the audio.** `captureSourcePerformanceViews` prepares its new host, constructs its new editor, then renders 32 blocks of 256 frames. `PluginEditor.cpp` clears the mailbox and resets the display in `Impl` construction. The helper does not construct another editor, call `prepareToPlay`, call `releaseResources`, or directly consume meter telemetry between rendering and the assertion. The processor's only explicit mailbox resets are prepare/release.

2. **The observed peak should be published.** `PluginProcessor.cpp::processBlock` scans the completed actual output channels after rendering and publishes their finite maximum. `OutputMeter.h` accumulates positive magnitude bits until consumption. In this offline fixture, DSP calls and message-loop dispatch happen on the same calling thread in sequence; there is no overlapping audio-producer/message-thread race during the 32-block render loop. The native host-meter oracle passed, and the fixture measured an ordinary normal float far above the display floor.

3. **The two GUI timers share one display.** The 24 Hz `MeterTicker` calls `updateMeter` when the editor implementation is showing. The editor's 8 Hz `timerCallback` calls `Impl::tick`, which calls the same `updateMeter` without that showing guard. Each update consumes the same processor mailbox into the same `outputMeterDisplay`. A second empty consume therefore decays the stored display peak; it does not replace it with zero. A transient `isShowing` change by itself cannot explain both paths missing the observation.

4. **A new reading is accepted after decay.** `OutputMeterDisplay::update` first decays its previous presentation state and then takes the maximum with the incoming finite sample peak. Waiting two seconds before the first callback does not age an unread mailbox peak to zero. The first callback should still display the newly consumed peak at approximately -21.6 dBFS.

5. **The source-label readiness check is not a timer witness.** `Impl` synchronously calls `syncSourceStatus` during construction. The helper's first `waitFor` can consequently succeed without any event-loop iteration. The initial floor label is also set synchronously by `buildTopBar`. The successful native-peer/showing and source-route assertions prove those states, but do not prove either normal meter timer ran during the later two-second wait.

6. **The two-second wait observes a deadline, not actual callback delivery.** Its loop pumps `runDispatchLoopUntil(20)` and checks the label until a `steady_clock` deadline. The exact JUCE 8.0.11 source used by CI was available locally at clean commit `c352e2489000ffeb9e397051377d75eef2efe641`. On macOS the dispatch helper runs the default CF/NS run-loop modes. JUCE's timer thread posts timer callbacks to the message thread; neither function promises a particular callback executes within a caller's wall-time budget under arbitrary scheduling. This establishes a plausible scheduling mechanism, but the failed log has no callback count, individual dispatch duration, or pending-mailbox sample proving that it happened here.

There is no evidence supporting a change to the DSP gain, mailbox algorithm, display release rate, native rendering mode, foreground state, or meter assertion. A hypothetical unobserved corruption or lifecycle error also cannot be excluded from the log alone. Calling the failure definitively flaky would overstate what was measured.

## The decay explanation is quantitatively excluded

The first fixture's peak is `-21.572142768 dBFS`. At the production release rate of 12 dB/second, reaching the -120 dBFS floor takes:

`(-21.572142768 - (-120)) / 12 = 8.202321436 seconds`.

The **entire** source-capture phase, including both fixture constructions and all four PNG saves, lasted only 6.355234 seconds. Even conservatively allowing decay for that whole phase yields approximately **-97.8349533 dBFS**, still above the floor. Publication actually happens after the phase starts, so this bound is deliberately generous. Ordinary decay therefore cannot produce the failed observation. The exact production class reproduced this bound in the small probe.

## Bounded mechanism probe

[`meter_state_probe.cpp`](../verification/a49/meter_state_probe.cpp) compiles directly against the unchanged production `OutputMeter.h` and `OutputMeterDisplay.h`; its command, exit status, and hashes are recorded in `evidence.json`. It uses synthetic samples and explicit clock values so its scope is clear.

The probe completed **7,130 checks with zero failures**:

- 2,001 possible initial poll delays from 0 through 2,000 ms all preserve and present the positive peak when the first callback consumes it.
- 5,125 initial phase combinations for JUCE's 41 ms and 125 ms timer intervals preserve a positive shared display across two seconds, including coincident callbacks.
- Withholding all display updates leaves the display at its initial floor while the mailbox still contains `0.0834435672`. The first update then produces `-21.5721436 dBFS` immediately.
- Decaying for the complete measured capture-phase duration still cannot reach the floor.

The withheld-dispatch case is a **state-machine mechanism demonstration**, not an assertion that native dispatch was withheld on the failing runner. It proves why callback-delivery evidence would distinguish an important hypothesis. It does not prove a JUCE, macOS, or scheduling defect.

The three existing local meter binaries also passed once: 20 mailbox checks, the display suite, and 22,769 independent audit checks. These are corroborating local checks, not native Intel acceptance. No GUI plugin build was available locally (`CS80_BUILD_PLUGIN=OFF`), and no large build was attempted. The full probe output is [`probe-output.log`](../verification/a49/probe-output.log).

The original `c5549f7d095a5c5f49a5ad22ec0ccc819245d201` Intel artifact contains a passing UI smoke run at **148.751 seconds**, with the same source fixture peak `0.0834435672` correctly displayed at **-21.6 dBFS**. That successful test's JUnit entry contains no stdout, so the evidence comes from its original full [`prior-c5549f7d-ui-smoke-lasttest-section.log`](../verification/a49/prior-c5549f7d-ui-smoke-lasttest-section.log), extracted from the native archive whose SHA-256 is `f0e2ae0152cb4fa910abe9b0bf512aac648868b7bd7801051a40f7655c9aacfb`.

This is evidence against an invariably failing meter/capture code path. It does not establish that the current failure is harmless, because the complete executable and other source files differ. The prior workflow also failed its library audit. **Its pass is not a replacement for current-source Intel acceptance.**

## Concrete next step and boundary

Keep the frozen source and existing assertion intact. After the active workflow finishes, perform the already authorized single complete Intel job rerun, retain the original failed attempt, and bind any new native/validator/install evidence to its actual job and source. A49 did not invoke or retry the rerun API. The root's earlier API rejection while Linux was still running does not count as a started rerun.

If the failure repeats, preserve both failures and instrument the snapshot helper before considering a fix. Useful narrowly scoped observations are the initial/final meter label, the number and maximum elapsed duration of dispatch calls, the dispatch helper's return value, final editor/showing state, and whether the original mailbox peak is still pending immediately after the failed assertion. Any diagnostic consume must occur only after the assertion has irrevocably recorded failure, be clearly identified as diagnostic, and never rescue the assertion or turn it into success. A counter for actual editor meter callbacks would separate failure of delivery from failure of telemetry/display state more directly, if a subsequent diagnostic source revision is warranted.

Do not silently extend the internal wait, call the timer synchronously, inject meter values, add an alternate consumer on the success path, remove the assertion, or claim the existing Intel archive passed. Those changes would either mask the observed contract failure or change what the smoke test establishes without a proven cause.
