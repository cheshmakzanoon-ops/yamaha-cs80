## Storage diagnosis and its limits

The original source declares an automatic `Engine` in both `main` and `captureLiveAdr`. `main` calls the live fixture before the default-fixture declaration executes, but its compiler-generated frame can already reserve storage for that declaration. The retained local disassembly confirms this behavior for the measured GCC build: the large `main` frame remains active at its call to `captureLiveAdr`.

The frozen `Engine` is **504,776 bytes** in the already retained [A45 constant-size measurement](../verification/a45/sizeof-results.json). It contains the current and previous retained instrument bodies. The local compiler's actual function-frame reports show:

| Local GCC 14.2 Release frame | Before | After |
| --- | ---: | ---: |
| `main` | 506,400 bytes | 1,616 bytes |
| `captureLiveAdr` | 507,888 bytes | 3,088 bytes |
| Both active capture frames | **1,014,288 bytes** | **4,704 bytes** |

The [static analysis receipt](../verification/a39/static-stack-analysis.json), [original stack report](../verification/a39/before-capture.stack-usage.txt), [repaired stack report](../verification/a39/after-capture.stack-usage.txt), and both retained `main` disassemblies bind these measurements to the actual local binaries. The reduction is **1,009,584 bytes**, before counting any nested Engine, library or runtime calls.

Microsoft documents a **1 MB default executable stack reserve** for x86, x64 and ARM64 in its [`/STACK` linker reference](https://learn.microsoft.com/en-us/cpp/build/reference/stack-stack-allocations?view=msvc-170). This repository's existing 8 MiB MSVC override applies only to executable target names matching `^cs80_.*tests$`; the `cs80_parity_capture` tool does not match. Its executable declaration links the core without a capture-specific stack override. The compiler may optimize automatic storage differently, as Microsoft's [stack-overflow debugging guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/debugging-a-stack-overflow) explains.

**Observed:** the original Windows exit is a stack-overflow status; the source has two large automatic capture objects; local GCC keeps their measured frames active together; the storage repair removes that demand. **Inferred:** these large active frames are the narrow cause consistent with the live-only native failure. The actual MSVC frame sizes, failing native instruction, backtrace and PE stack reserve were not measured. Local GCC frame sizes are not presented as Windows measurements.

No artificial fault reproduction or constrained-stack execution was performed. All local capture and test processes used the ordinary unchanged Linux stack limit of **8,388,608 bytes**, with unlimited hard limit. The original native failure remains a failure and is not replaced by local evidence.
