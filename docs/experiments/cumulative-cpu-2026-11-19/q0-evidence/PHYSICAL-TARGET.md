# A separate physical-target test, not a repeat of the failed guest session

**Nothing in this package ran on physical target hardware.** The original cloud Q0 is closed. A different, dedicated physical machine and a newly registered experiment can answer a different question: *Does this pinned final build meet a stated budget on this particular low-end machine?* A single target is not evidence for every weak computer. A VM limited to two/four vCPUs is not a representative old physical CPU.

### 1. Calibrate the actual machine and clock first

Use the repository's [stock-only target qualification](https://github.com/cheshmakzanoon-ops/yamaha-cs80/blob/5ef3cfee8a7b0a25a632c2cdc6cb01b1bbfba8c4/tools/vst3-target-qualification/README.md) and [frozen methodology](https://github.com/cheshmakzanoon-ops/yamaha-cs80/blob/5ef3cfee8a7b0a25a632c2cdc6cb01b1bbfba8c4/tools/vst3-target-qualification/METHOD.md) on an explicitly authorized dedicated Linux x86-64 target. Identify the actual CPU SKU/year, physical and logical core counts, SMT state, OS/kernel, cooling/power configuration and what the OS can actually report. Pick an allowed core with an idle sibling if applicable; no competing profiler, build or benchmark. Pin the JUCE/VST3 SDK, toolchain/flags, authentic stock ELF and hash independently; rebuild the *same tag and settings* with documented hashes if required by an older supported ISA/runtime. No service needs to alter governor/security settings or access anyone's existing computer.

The repository's **single-core** stock qualification suits 2C/2T or 4C/4T Linux targets. An operator uses the documented build, `run.py inspect`, untimed `smoke`, then one `collect --dedicated-target` and `analyze.py <session>/summary.json`. It rejects detected virtualization; an absence of detection alone is not proof. All 12 fresh-process triplets (held/eight notes, 48 kHz, 64 frames) must report genuine paired data and public state/audio parity. With the existing method, the equal-stock and matched-positive-common 95% intervals must fit −2% to +2%, and the known +6.25% extra-call interval +3% to +10%. This is **not** the cloud Q0's +12.5% control, and it tests neither the final treatment nor idle. Retain complete failures and stop; do not re-label them as calibration or lower tolerances. The five-scene guest crossover requires four distinct worker CPUs and a separate supervisor: it is not directly deployable unchanged on a 2C/2T or 4C/4T target.

### 2. State exactly what 15% or 2% means

For the callback budget, use **timed callback-thread CPU seconds divided by rendered stereo timeline seconds**. At 48,000 Hz and 64 frames the denominator per callback is 64/48,000 = **1.333333 ms**, once per stereo block, not twice for stereo and not doubled for 2× oversampling. For N equal blocks, RTF = Σ native callback thread CPU ns ÷ (N × 64/48,000 × 10⁹). Thus:

| Stated target | What the mean budget is at 48 kHz/64 |
|---|---:|
| Eight held source voices, Standard 2×: RTF ≤0.15 | **200 µs** callback CPU per block; 15% of one CPU-second per audio-second |
| Fresh quiet, same settings: RTF ≤0.02 | **26.667 µs** per block; 2% of one CPU-second per audio-second |

A whole-process or machine percentage is a **different measurement**. If “2% on 4C/4T” or “4% on 2C/2T” denotes a fraction of *all* equal logical CPUs at real-time playback, the corresponding arithmetic budget is **0.08 CPU seconds per second** for either box (106.667 µs/block equivalent). It is **not** the project’s 0.15 RTF goal. Do not divide by core count and call it a measured process result: host/UI, worker threads, drivers, and other work are not inside the plug-in's callback. For a whole-process claim, separately observe **Δ CPU time of all threads in a specified process ÷ (wall duration × online logical CPUs)** during **real-time-paced playback**, report the count and whether the host/UI/driver is included, and give the undivided one-core-normalized figure as well. For a DAW meter/deadline claim, use the named DAW, driver/device, sample rate, buffer, p95/p99/max wall durations, misses and xruns; mean callback RTF is not a glitch guarantee.

### 3. Register a new, single-core, real-plug-in product trial

Only after target stock calibration passes, separately predeclare final source/ELF/ISA identity, CPU treatment/placement, independent epoch count and intervals, workload and admission criteria **before** collecting product times. Do not splice the guest samples or relax the older rules. Use the pinned real VST3 and headless host, not a linked DSP microbenchmark or guest instruction counts. Use eight held varied velocities and fresh quiet for the two separate absolute targets, with factory settings, sample rate, 2× and block size frozen. Include original/original controls in **both** scenes (fresh quiet is not qualified by held-only calibration), verified isolated audio/FP/state/continuation parity, known-extra-work controls, and no exclusions. Do not call all idle histories qualified without also testing equal- and varied-release tails. To evaluate the *relative* shipped change as well, prospectively add original/final pairs and contemporaneous original/original controls; report absolute cost and uncertainty separately from the paired relative effect.

One conservative absolute decision is that the upper 95% bound of prespecified epoch-log RTF for the final image lies **at or below each target**, with all corresponding controls passing. State the estimator (geometric mean across independent epochs is not a p99 or an arithmetic mean) and publish unaggregated epoch totals, tails and every failure; if claiming an arithmetic-mean budget, predeclare its estimator and interval instead. A slow but stable machine can pass clock qualification while the plug-in still misses its budget. This document describes a possible future physical test, not authorization to run one.
